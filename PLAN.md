# Property Management System — Development Plan

A web app for landlords to register properties, track income/expenses, manage tenants & leases, and handle maintenance requests.

## Recommended Tech Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 15 (App Router) + React 19 | SSR, Server Actions, API routes in one |
| Language | TypeScript | Safety across the stack |
| UI | Tailwind CSS + shadcn/ui | Fast, accessible, consistent components |
| Database | Supabase (Postgres) *or* Neon Postgres + Prisma ORM | Managed, cheap, scales |
| Auth | Auth.js (NextAuth) — credentials + Google OAuth | Flexible, Next.js native. Clerk = faster alternative |
| File storage | Cloudflare R2 / S3 | Property & maintenance photos |
| Email | Gmail SMTP or Resend | Transactional notifications; Gmail needs no domain |
| Payments (Phase 2) | GCash + bank transfer (manual, owner verification) | Rent collection (send-money/transfer + reference flow with owner verification), receipts |
| Deploy | Vercel + Supabase/Neon | Zero-config |

## Architecture

- **Route groups:** `(marketing)` landing/auth · `(dashboard)` landlord app (protected) · `(tenant)` tenant portal (protected)
- **Data access:** Server Components + Server Actions (or tRPC if you prefer explicit APIs)
- **Multi-tenancy:** every table scoped by `userId`/`orgId`; enforce scoping in every query (use RLS if Supabase). **Portfolio (shipped):** ownership lives in a `portfolios` bucket with a `portfolio_members` pivot (roles `owner` / `co_owner` / `viewer`) — properties, tenants and custom-field definitions belong to the portfolio, so a co-owner sees the portfolio's whole context including the same custom fields as the primary owner. Billing stays on the account and a portfolio's quota is its owner's plan. See `PORTFOLIO.md`
- **Roles:** `users.role` — `landlord` / `tenant`; the session callback exposes it and login routes by it. Dashboard access is role-gated (`tenant` → portal), but **portal access follows the data**: any account linked to a `tenants` roster entry (`tenants.account_id`) can use the portal, so an owner who rents from another owner gets both. The portal layout allows a linked profile through and redirects unlinked landlords to the dashboard

## Data Model (Prisma sketch)

- **User** — landlord account (email, hashed password, plan)
- **Property** — address, type, photos, units[]
- **Unit** — propertyId, name/number, bedrooms, rentAmount, status (vacant/occupied)
- **Tenant** — name, phone, email
- **Lease** — unitId, tenantId, start/end dates, rent, deposit, status
- **Meter** — unitId, type (electric/water), label, default rate
- **MeterReading** — meterId, periodMonth, previous/current reading, consumption, rate snapshot, amount
- **Charge** — leaseId, periodMonth, type (electricity/water/dues/penalty/other), amount
- **Payment** — leaseId, amount, date, method, type (rent/late fee), status (pending/paid/rejected)
- **Expense** — propertyId, category, amount, date, vendor
- **MaintenanceRequest** — unitId, tenantId, title, description, priority, status (new → in progress → resolved), photos
- **Document** — leases, inspection reports
- **Notification** — in-app + email log

## MVP Feature Set (Phase 1)

1. Auth: register/login, email verification, Google sign-in (optional)
2. Dashboard KPIs: occupancy rate, income this month, open requests, expiring leases
3. Properties & units: CRUD with photo uploads
4. Tenants & leases: CRUD, lease-end alerts
5. Finance: record payments & expenses, recurring rent, simple P&L per property
6. Maintenance: create/update requests, status workflow, photos
7. Email notifications (new request, rent due, lease expiring)

## Phase 2

- ~~Stripe rent collection~~ **GCash rent collection** ✅ — the tenant portal's pay-rent flow now runs on GCash, the dominant PH wallet: the landlord saves their GCash number under **Settings** (new `/settings` page, `users.gcash_number`/`gcash_name`); tenants open the pay-rent page which shows the wallet + exact amount + send-money steps, then submit the **reference number** from their GCash confirmation (`confirmGcashPaymentAction` — validates, records a **pending** payment with method `gcash` and note `GCash payment — Ref #N`; re-submitting the same reference can't double-record). The landlord verifies references against their GCash history — pending submissions are surfaced in a **Verify / Turn down** queue on the Finance page (see the verification bullet below). Stripe was **removed** (webhook route, `stripe` dep, demo fallback) — the reference flow needs no merchant account or gateway; a PayMongo/Xendit integration (GCash + Maya + QR Ph, ~1.3% MDR) is the upgrade path if merchant checkout is ever wanted
- ~~Card rent collection (PayMongo)~~ **Bank rent collection** ✅ — the tenant card checkout (hosted PayMongo sessions + webhook) was **removed** at the landlord's request, together with `startCardCheckoutAction`, the `/portal/pay-rent/[id]/card` page, `src/lib/payments/`, the `/api/payments/paymongo/webhook` route, the `payment_checkouts` table mapping, the `card` value in the `payment_method` enum (legacy rows map to `other`), and the PayMongo env vars in `.env.example`. In its place tenants can now pay by **bank transfer**, the same manual send-money + reference + owner-verification flow as GCash: the landlord adds bank accounts under **Settings → Bank accounts** (`bank_accounts` table — dropdown of major PH banks or "Other" to type the name, plus account number and account name; `createBankAccountAction` / `deleteBankAccountAction`), and the pay-rent page (`/portal/pay-rent/[id]`) is a two-method chooser that forwards straight to GCash when no bank account is saved. The bank-transfer page (`/portal/pay-rent/[id]/bank-transfer`) lists the landlord's active accounts and send-money steps, then `confirmBankTransferPaymentAction` records a **pending** payment (method `bank_transfer`, note `Bank transfer — Ref #N`, `payments.bank_account_id` pointing at the destination account, validated against the landlord's own active accounts so a forged id can't name someone else's). Verification is the existing Finance **Verify / Turn down** queue — pending rows appear there regardless of method, approval flips the row atomically and emails the receipt, and a rejected reference can be resubmitted (which reopens it and can re-point the destination account)
- Tenant portal (view lease, pay rent, submit requests) ✅
- **Utility sub-metering + per-tenant monthly statements** ✅ — per-unit electric/water meters (rate mode), batch readings upserted by (meter,month), manual charges for split bills, computed statements (rent+utilities+charges−payments), lease edit shows statement with add/delete charges, portal shows statement and collects outstanding balance.
- **GCash payments require the owner's verification** ✅ — a submitted reference no longer counts as money by itself. `payments.status` (`pending` / `paid` / `rejected`, defaulting to `paid` so every existing record and every landlord-entered or gateway-settled payment is unaffected) models the review: portal submissions land `pending`, so they appear as *Awaiting verification* in the tenant's payment history and stay **out of the statement, income KPIs, reports, and the health score's rent-collection ratio** until the owner approves them. Finance gains an **Awaiting verification** card listing each submission with its reference and **Verify / Turn down** buttons (`verifyPaymentAction` / `rejectPaymentAction`, manage-rights only). Approval flips the row atomically (`UPDATE … WHERE status = 'pending'`, so a double-click can't send two receipts) and then emails the tenant their receipt; turning one down keeps it on record as rejected, and resubmitting the same reference **reopens** it for review at the current balance. The portal shows the pending total as a warning ("not yet included in your balance") so a tenant isn't asked to pay twice while a reference is under review. `src/lib/rent-payment.ts` holds the claim/verify/reject logic.
- **Owners can be tenants too** ✅ — an owner who rents from another owner uses the same account for both sides. Portal access is granted by the **linked tenant profile**, not the account's role: `src/lib/portal-access.ts` (`userHasTenantProfile`) gates the portal layout and the sidebar/portal headers expose a switch link (`Tenant portal` ↔ `Dashboard`). The invite flow now **links an existing account instead of refusing it** — sending an invite to an address that already has an account is allowed (only an address already tied to another landlord's roster is rejected, since the portal resolves one profile per login), and `/api/auth/complete-portal-setup` links the roster row to that account **without touching its password** (`{ linkedExisting: true }` sends the owner to sign in with their usual credentials rather than auto-signing in). Critically, **revoke no longer deletes a landlord's account**: only a tenant-only account is deleted (its reports are reassigned first); an owner-tenant is simply unlinked, so their properties and login survive. Portal server actions rely on the profile lookup alone (the `role === "tenant"` checks are gone)
- **Sign in with Google** ✅ — an optional second front door beside email/password, registered in `src/auth.ts` only when `AUTH_GOOGLE_ID` + `AUTH_GOOGLE_SECRET` are both set, so an unconfigured deployment never advertises a provider it can't finish (Settings → **Sign-in** shows the live state plus the exact redirect URI to paste into Google Cloud Console, mirroring the PayMongo webhook card). The "Continue with Google" button is rendered by a **server** gate (`src/lib/auth-providers.ts` → `googleSignInEnabled()`): `/login`, `/register`, and `/portal-setup` are now server components (or read the flag per request) that pass `googleEnabled` to their client forms, so a secret never reaches the bundle. Login reads `?error=` too and maps Auth.js's codes (a refused callback, a missing secret, an expired link) to plain sentences instead of a dead-end redirect. Google is trusted to verify the address — every account here is only created after its email was proven (signup OTP, tenant invite) — so `allowDangerousEmailAccountLinking` is on, which is what lets an invited tenant, or an owner who also rents, sign in either way and still reach **one** profile (the JWT then carries that account's real role, so a Google sign-in that links a tenant stays a tenant). The avatar URL is truncated to `varchar(255)` so an unusually long one can't fail the insert — note the app never gates on `users.email_verified` (an email signup proves the address by OTP, and OAuth is trusted on Google's own verification), so Auth.js's default of leaving it null for OAuth users is harmless. New Google accounts default to `landlord` + `free`, identical to an email signup; `/dashboard` is the shared callback and the dashboard layout forwards tenants to `/portal`. **The tenant invite accepts Google too**: `/portal-setup` shows the button, returns to itself with the invite token, and the signed-in account claims the invite through `claimInvitationForAccount` (`src/lib/tenant-invitations.ts`) — the emailed token proves control of the address, so a wrong-account click is refused **before** the single-use link is spent (previewed, then claimed atomically). A fresh Google account that owns nothing and has never set a password is flipped to `tenant` (matching the password path) so it lands in the portal; an existing landlord who rents keeps their role and just gains the portal link.

## Phase 3

- **PWA / mobile-first polish** ✅ — installable to the home screen: `app/manifest.ts` (standalone display, `start_url: /dashboard` so the launcher role-routes like the app does, emerald `theme_color`, Dashboard/Finance/Maintenance app shortcuts, PNG icons at 192/512 plus a full-bleed **maskable** variant rasterized from the SVG logo), a deliberately conservative `public/sw.js` (never touches `/api` or non-GET; navigations are network-first with a branded `public/offline.html` fallback and HTML is never cached; hashed `/_next/static` + icons are cache-first), an install prompt that uses the native `beforeinstallprompt` sheet on Chromium and spells out Share → Add to Home Screen on iOS (dismissal persists in localStorage), and mobile polish: `viewport-fit=cover` with `env(safe-area-inset-*)` padding on both app headers, the drawer and the sidebar footer, `overscroll-contain` on the drawer, and `nosniff`/`DENY`/referrer headers plus `no-store` + CSP on `sw.js`. The SW registers **in production only** so dev HMR stays honest.
- **Tenant-reported media (photos + video)** ✅ — the portal's "Report an issue" form takes up to **3 files** (images plus short MP4/MOV/WebM clips), previewed as thumbnails with per-file size and a remove button before sending. Photos are **re-encoded in the browser** (`src/lib/media-client.ts`: 1600px long edge, JPEG q0.82) because a modern phone photo is 3–5MB while a serverless request body caps out around 4.5MB — an 18MB test photo lands at 901KB, so three photos and a clip fit comfortably. Files land in `documents` through the new nullable `maintenance_request_id` and show as thumbnails on the tenant's portal list **and** in the landlord's Maintenance row. The documents route now serves images **inline** (so they can be thumbnails) with `?download=1` forcing an attachment, keeps everything else as a download, and grants the reporting tenant access to their own uploads even after their lease has ended; a failed attachment never swallows the report. Real video volumes still need R2/S3 — the honest limit today is short clips
- **Lease notes + attachments** ✅ — every lease page now carries free-text **Notes** (new `lease_notes` table: author, timestamp, author-only delete, 2000-char cap) and **Attachments** using the previously-unused `documents` table, now carrying a `data` column. Files are stored **in Postgres as base64** rather than written to `public/`, because Vercel's filesystem is read-only at runtime — anything written there would vanish on redeploy, and object storage (R2/S3) is still parked for lack of credentials. Downloads go through `/api/documents/{id}`, which re-checks lease/unit/property access before streaming and always serves `Content-Disposition: attachment` (never inline, so an uploaded file can never execute in the app's origin). Uploads are **allowlisted** by MIME type (PDF, images, Word/Excel/text — HTML and SVG deliberately excluded), capped at 5 MB with `serverActions.bodySizeLimit` raised to 8 MB for multipart overhead, and filenames are sanitised before storage and again in the download header. Moving to R2 later only means nulling `data` and putting a key in `url`
- **Lease signing (no vendor)** ✅ — both parties sign in-app, so a lease can be executed without DocuSign/Dropbox Sign: `lease_signatures` table (one row per party per lease, unique on lease+role, so re-signing replaces), a **Signatures** card on the lease edit page and in the tenant portal, and a shared `SignatureDialog` where a party either types a name (rendered in a local script font — no web font needed) or draws a mark on a pointer/touch canvas stored as a PNG data URL (400KB cap). Both paths require an explicit electronic-signature attestation, which is what makes either one binding; the checkbox is controlled because React clears uncontrolled fields when a form action settles. `/leases/{id}/signed` renders a print/PDF-ready copy with both signatures, dates and methods. Landlord-side and tenant-side actions are separate (`signLeaseAction` gated by `canManageUnit`, `signLeaseAsTenantAction` scoped to the tenant's own lease) but share `src/lib/signatures.ts`. DocuSign/Hellosign can slot in later by adding provider/envelope columns without changing the UX; tenant screening still needs credentials
- E-sign vendor (DocuSign/Dropbox Sign) + tenant screening — parked until credentials exist
- QuickBooks/Xero integration — parked (needs an OAuth app)
- **Forgot / reset password** ✅ — `/forgot-password` (linked from the sign-in card) emails a one-time link; `/reset-password?token=…` sets the new one. `password_reset_tokens` stores **only the SHA-256 hash** of a 32-byte token, so a leaked DB row or backup can't be replayed into a working link; tokens are single-use and expire after 60 minutes. The request action **always** returns the same confirmation whether or not the address is registered — a different reply for unknown addresses would turn the form into an account-enumeration oracle — and a 10-minute resend cooldown (keyed on the newest *unused* token, since minting one deletes the previous) silently absorbs repeat requests. A reset stamps `users.password_changed_at` and the `jwt` callback returns `null` for tokens minted before it, signing other devices out: that is the only hook that works, because server-side `auth()` re-attaches the token as `session.user` and a session callback cannot remove it (cost: one indexed `users` lookup per session read). `session.maxAge` is now an explicit 7 days. Tenant accounts use the same flow and land on `/portal` afterwards
- **AI: expense categorisation + rent suggestions** ✅ (built against the "LLM seam + honest fallback" pattern — `src/lib/ai.ts` makes one OpenAI-compatible `chat/completions` call over plain `fetch`, so no SDK is needed and `AI_API_KEY` / `AI_BASE_URL` / `AI_MODEL` switch providers; with no key every helper returns null and the callers fall back to deterministic rules)
  - **Expense categorisation** (`src/lib/expense-intelligence.ts`) in the expense dialog, debounced as the vendor/notes are typed. Order of trust: **the landlord's own history for that vendor** (repeat bills are the common case and their bookkeeping beats any guess — "You filed 3 of 3 past Meralco expenses as this"), then the model, then vendor/keywords. A category the user picks themselves always wins over a suggestion, and with no signal at all nothing is shown rather than a weak guess.
  - **Rent suggestions** (`src/lib/rent-insights.ts`) on the unit dialog: comparable units in the same property (falling back to the city), **occupancy-weighted median** — occupied units count double, since that is a rent the market has actually accepted — plus a 25th/75th percentile range, rounded to ₱500. It never claims market data it doesn't have; the reasons line says exactly what it looked at. With a model configured the same comparables are handed over for judgement, **clamped to ±60% of the computed median** so a hallucinated number can't escape into the UI.
  - Both chips are explicitly badged **AI** or **RULES** so a rule-based guess is never passed off as AI. Access is checked in SQL (a crafted unit id can't pull another landlord's comparables). Enabling the model = adding `AI_API_KEY` (+ optionally `AI_BASE_URL`/`AI_MODEL`) to `.env.local`/Vercel; nothing else changes.
- **Email OTP at registration** ✅ — `/register` collects name/email/password, then asks for a 6-digit code before the account exists. The signup is held in **`pending_registrations`** (`src/lib/email-verification.ts`) and only becomes a `users` row when the code comes back, so an unverified address never holds a usable login and abandoned signups can't lock an address out (rows expire and are purged). Codes are 6 digits, expire after 15 minutes, allow **5 wrong guesses** (the 5th destroys the row and forces a fresh request), and are stored as an **HMAC-SHA256 keyed with `AUTH_SECRET` over `email:code`** — a bare hash of six digits falls to an offline sweep of a million values, and binding the address stops a code being replayed against another signup. The pending row is claimed with `delete … where code_hash = … returning`, so two parallel submissions can't both spend the same code. A 60-second cooldown on both starting and resending keeps the form from being used as a mail cannon; `/api/auth/resend-code` answers **identically** for an address with no signup waiting, so it can't be used to test who has an account. The verified user is created with `email_verified` already set (the address *was* proven), and sign-in is unchanged — tenants created by landlords never see this. A wrong code keeps you on the form; a burned or expired one drops back to the details step to start over.

### Dev-environment gotchas (learned the hard way)

- **CSS/theme edits need `rm -rf .next` + a dev-server restart.** The custom `turbopack.rules` entry for `*.css` in `next.config.ts` caches the compiled stylesheet, so Turbopack keeps serving the old chunk (same filename hash) even after a full restart — theme changes look like they simply didn't happen. Clear `.next` after touching `globals.css`.
- The Next dev indicator defaults to **bottom-left**, where it sits on top of the sidebar footer's theme toggle and sign-out button and swallows clicks. `devIndicators.position` is set to `"bottom-right"` in `next.config.ts`.
- Playwright: `button[aria-label="…"]` matches three toggles across desktop sidebar / mobile header / drawer — scope with `:visible` or a container locator, or clicks hit hidden elements.
- Never edit markdown with PowerShell `Get-Content`/`Set-Content` round-trips — it mangles em dashes into U+FFFD. Use the edit tool or Node (`fs.readFileSync/writeFileSync` with `\uXXXX` escapes).
- **A long-running dev server can hold a stale module graph after `src/db/schema.ts` gains a new table** — a new module importing it gets `undefined` instead of the export, surfacing as `Cannot read properties of undefined (reading '<column>')` in a route handler. Restart `next dev` after adding a schema table; no `.next` wipe needed.
- **`AUTH_URL` is the host every link inside an email is built from**, and `.env.local` and the Vercel project need *different* values (`http://localhost:3000` vs the deployment URL). A stale one makes sending look broken while it silently works. **Settings → Email delivery** shows the configured sender + link target, sends a real test message and reports the provider's verdict, and warns when `AUTH_URL`'s host doesn't match the site being viewed. Two more traps it surfaces: `example.com` recipients are rejected by Resend in all environments, and the shared `onboarding@resend.dev` sender only delivers to the address on the Resend account — so **test addresses are `logo-demo@example.com` (never receives) and a real mailbox (always receives)**.
- **Gmail SMTP is the no-domain sender.** Set `GMAIL_USER` (the full Gmail/Workspace address) and `GMAIL_APP_PASSWORD` (16 characters, generated at `myaccount.google.com/apppasswords`). App passwords require **2-Step Verification** on the account — with it off, Google rejects any generated password with `535-5.7.8 Username and Password not accepted`. Unlike Resend's shared sender it reaches *any* recipient, so it's the right choice until a sending domain is verified. Two traps: Gmail only sends as the authenticated address, so `EMAIL_FROM` must equal `GMAIL_USER` or it is ignored (the app then sends as `RentBase-PH <GMAIL_USER>` and warns once in the log), and a free Gmail account is capped at ~500 recipients/day (2,000 for Workspace) — fine for beta, not for scale. `nodemailer` must stay listed in `serverExternalPackages` in `next.config.ts`: it does runtime `require`s of optional deps that break when Next bundles it.
- **PayMongo card checkout was removed** (the landlord's manual bank-transfer flow replaced it): `PAYMONGO_SECRET_KEY`/`PAYMONGO_WEBHOOK_SECRET`, `src/lib/payments/`, `/api/payments/paymongo/webhook` and the `payment_checkouts` mapping are gone. Any PayMongo dashboard webhook left pointing at that URL now 404s, which is expected — delete it. What remains is the send-money + reference + owner-verification rail shared by GCash and bank transfer.
- **Google sign-in needs a redirect URI that matches *the origin the browser is on*.** Create a **Web application** OAuth client (Google Cloud Console → APIs & Services → Credentials), set `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`, and register `<AUTH_URL>/api/auth/callback/google`. Because `AUTH_URL` differs between local (`http://localhost:3000`) and production, list **both** URIs on the same client — a missing one fails as Google's own `redirect_uri_mismatch` screen before the app is even reached, so add the production URI the moment the domain exists. There is no client secret in the browser bundle: `/login` and `/register` are server components that pass a plain "Google is configured" boolean down, and the provider isn't even registered until both env vars exist, so a deployment without them simply shows the email form. The one behavioural quirk worth knowing: enabling `allowDangerousEmailAccountLinking` means a Google account **links onto** an existing email/password account instead of erroring — safe here only because the address is Google-verified *and* every account in this app was email-proven before it existed (signup OTP, tenant invite); if an email provider that doesn't verify is ever added, revisit that flag.
- The password-reset resend cooldown is silent *by design* (enumeration), so a retry inside 10 minutes sends nothing while still saying "check your inbox" — it logs `[password-reset] request suppressed by the resend cooldown` instead. A throttle that hides itself like this reads as a broken feature; check the server log before assuming mail is failing.
- **Blanking an env var in a shell command does nothing on Windows** — cmd.exe can't represent empty-valued variables, so `$env:RESEND_API_KEY = ""` is dropped before `npx`'s `.cmd` shim spawns and Next quietly loads the key from `.env.local` anyway (the tenant invite then hits Resend and 422s instead of logging). To test a flow as if no key exists, comment the line out in `.env.local` and restart — the emailed setup link then shows up as `[email:dev]` in the server log, which is where the test scripts read it from.
- Playwright: **anchor URL regexes** — `waitForURL(/\/portal/)` also matches `/portal-setup`, so the assertion "passes" while the page never navigated, and a follow-up `context.close()` kills the in-flight submit so the endpoint itself looks broken. Use `/\/portal$/`. A failed UI assertion also isn't proof of a bad server response — dump the whole card (or the server log) before debugging the API.
